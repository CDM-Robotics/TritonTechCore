# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TritonTechCore is a reusable FRC (FIRST Robotics Competition) Java library from CDM Robotics. It targets **WPILib 2027 (currently `2027.0.0-alpha-7`) on the SystemCore controller**, uses Java 25 and Gradle 9.4.1, and does not support the roboRIO. It is **not** a WPILib robot project: it has no `Robot` class, no deploy block, and no `.wpilib/` preferences. It is published to Maven Local as `org.tritontech:TritonTechCore`. The robot project (`../2026_Main-Imported`, branch `wpilib-2027`) consumes it with `mavenLocal()` and `implementation 'org.tritontech:TritonTechCore:2.+'`. It does not use the generated `TritonTechCore.json` vendordep. Major version 1.x is the 2026/roboRIO line; 2.x is 2027/SystemCore. The original 2026 robot project (`../2026_Main`) is pinned to `1.+`.

The last 2026/roboRIO version is commit `6d03359` (published locally as `1.0.32`).

## Commands

Use Git Bash (`./gradlew`) or `gradlew.bat` on Windows. The code compiles with a JDK 25 toolchain. Gradle itself can run on any JDK 17 or newer, and `gradle.properties` registers the WPILib-bundled JDK (`C:/Users/Public/wpilib/2027_alpha7/jdk`) as a toolchain, so `JAVA_HOME` doesn't need to be set. When the WPILib year changes, update that path. `settings.gradle` resolves GradleRIO from the local WPILib install's Maven repo first, then from the Gradle plugin portal, which is what CI uses.

```bash
./gradlew clean build --refresh-dependencies   # full build + tests (also regenerates TritonTechCore.json)
./gradlew test                                  # run tests only
./gradlew test --tests org.tritontech.core.SwerveUtilsTest                   # single test class
./gradlew test --tests 'org.tritontech.core.SwerveUtilsTest.testWrapAngle*'  # single test / pattern
./gradlew publishToMavenLocal                   # publish to ~/.m2 for the robot project to consume
./gradlew bumpPatchVersion                      # bump PATCH in build.gradle (local only, no network)
./gradlew cleanEclipse eclipse                  # regenerate VS Code/Eclipse project files when the IDE cache is broken
```

There is no linter configured. Only `SwerveUtils` has unit tests, because the other classes need hardware/HAL (REV Sparks, NavX, PhotonVision).

## Versioning and local publishing workflow

The version lives only in `version = 'X.Y.Z'` in [build.gradle](build.gradle). Everything else derives from it: the published Maven coordinates, the generated `TritonTechCore.json`, and `version.properties`, which `VersionManager` reads at runtime and prints on class load.

- **MINOR is owned by CI.** On every push to `main`, [ci.yml](.github/workflows/ci.yml) increments MINOR, resets PATCH to 0, and commits `build.gradle` back to `main`. Pull before you work locally, because `main` will have moved ahead of your last push.
- **PATCH is owned by local dev.** To test changes in the robot project, run these as **two separate Gradle invocations**:
  ```bash
  ./gradlew bumpPatchVersion
  ./gradlew publishToMavenLocal
  ```
  They cannot be chained or wired via `dependsOn`, because Gradle locks in `project.version` during configuration. A fresh version string forces the robot project to re-resolve the jar instead of reusing a cached one.
- `TritonTechCore.json` is gitignored and generated by `generateVendorJson`, which runs on `build` and `publishToMavenLocal`. It points `mavenUrls` and `jsonUrl` at `C:/Users/<user>/...` paths, so it is meant for local Windows use.

## Dependencies

Vendor libraries come from the JSON files in [vendordeps/](vendordeps/) via `wpi.java.vendor.java()`: CommandsV2 (shipped with WPILib), REVLib, PhotonLib, ChoreoLib and AdvantageKit. Every vendordep's `wpilibYear` must match the installed WPILib (`2027_alpha7`). Vendors publish 2027 builds at different URLs from their 2026 ones:

- **REVLib**: `https://software-metadata.revrobotics.com/REVLib-2027.json`
- **ChoreoLib**: `https://choreo.autos/lib/ChoreoLib2027Alpha.json`
- **AdvantageKit**: `v27.0.0-alpha-*` GitHub releases. Its embedded `jsonUrl` points at "latest", which is still 2026, so don't trust the VS Code updater for it.
- **PhotonLib**: the tagged `v2027.0.0-alpha-2` targets WPILib alpha 5, so this repo uses a `dev-…` build from the PhotonVision "Dev" GitHub release that targets `2027_alpha7`.
- **Studica/NavX**: removed. SystemCore has no MXP port; the drivetrain uses SystemCore's built-in `OnboardIMU` instead.

CommandsV2 and CommandsV3 cannot both be present. PathPlanner was removed in favor of Choreo, and its imports are left commented out.

## WPILib 2027 API notes

These are easy to get wrong when porting 2026 code:

- **Packages**: `edu.wpi.first.*` became `org.wpilib.*`. For example, `org.wpilib.math.geometry`, `org.wpilib.math.linalg.Matrix`, `org.wpilib.math.util.MathUtil`, `org.wpilib.command2.*` and `org.wpilib.driverstation.DriverStation`.
- **Kinematics**: `ChassisSpeeds` became `ChassisVelocities` (fields `vx`, `vy`, `omega`). Field-relative conversion is `new ChassisVelocities(...).toRobotRelative(heading)`. `SwerveModuleState` became `SwerveModuleVelocity` (field `velocity`).
- **No more in-place mutation**: `SwerveModuleVelocity.optimize()` and `SwerveDriveKinematics.desaturateWheelVelocities()` now **return new objects**. Ignoring the return value compiles but silently does nothing.
- **Dashboard**: `SmartDashboard` is gone. Use `org.wpilib.telemetry.Telemetry.log(key, value)`.
- **Field layouts**: `AprilTagFieldLayout` became `org.wpilib.fields.Field` (`Field.loadField(Fields.X)`, `getTags()` returning `FieldTag`, and `getTagPose(id)`).
- **Xbox buttons**: on `CommandXboxController`, `back()` and `start()` became `view()` and `menu()`.
- **Unused commands**: WPILib's javac plugin fails the build if a `Command` is created and never used.
- **REVLib**: Spark constructors take a `CANPort` (SystemCore has several CAN buses). Encoder getters, `getOutputCurrent()`, `getBusVoltage()` and `getSetpoint()` return `Signal<Double>`, so call `.get()`.
- **REVLib units**: encoder conversion factors are **gone**. Encoders always report native rotations and RPM, and closed-loop setpoints use those units too: position in rotations, velocity in RPM. Closed-loop gains therefore act on native units. `SwerveModule` converts at the boundary using its `drivingMetersPerRotation` argument, and the turning absolute encoder uses 2π radians per rotation. Also gone or renamed: `velocityFF` (now `closedLoop.feedForward.kV`, in volts per RPM), `pidf` (now `pid` plus `feedForward`), `positionWrappingInputRange`, `uvw*` encoder settings, and `forward/reverseLimitSwitchEnabled` (use `...TriggerBehavior(kKeepMovingMotor)`).
- **PhotonLib**: `PhotonPoseEstimator(Field, robotToCam)` no longer takes a `PoseStrategy`. Call `estimateCoprocMultiTagPose(result)`, `estimateLowestAmbiguityPose(result)` and so on directly.

## Architecture

Everything is in the single package `org.tritontech.core`. Every public class has a `static { VersionManager.initialize(); }` block so the library version is logged once, whichever class loads first. Keep this pattern in new classes.

- **`SwerveModule`**: one REV MAXSwerve module (a driving and a turning Spark, a Through Bore absolute encoder on the turning motor, and a per-module chassis angular offset). Motors are created through `MotorFactory` and `MotorControllerType`, so each module can mix SPARK MAX and SPARK FLEX. Constructor overloads that don't take a `CANPort` use `MotorFactory.DEFAULT_CAN_BUS` (`CAN_S0`). The last constructor argument, `drivingMetersPerRotation`, is the wheel travel per driving motor rotation. The configs passed in must not rely on conversion factors, and their gains are in native units: RPM for driving, rotations for turning. The robot project passes in its `SparkBaseConfig`s and feedforward; this library does not hard-code tuning.
- **`DriveTrain`** (`SubsystemBase`): the central class. It owns the four modules, SystemCore's `OnboardIMU`, and an optional `Vision`. The IMU's `MountOrientation` is a constructor argument and defaults to `FLAT`. Important details:
  - **Two-phase configuration.** After construction, the robot project must call `setDriveConstants(...)`, `setChassisConstants(...)`, and also `setVisionConstants(...)` if a `Vision` was passed. Until then, `drive()` prints a one-time warning and returns without moving.
  - **Two pose estimators.** `m_measuredOdometry` always fuses vision measurements. `m_currentOdometry` is what `getPose()` returns and what autos use, and it only fuses vision when `setOdometryToLiveUpdate(true)` is set. `syncOdometryToVision()` copies the measured pose into the current one.
  - **Heading** is `getAngle()`: the IMU yaw wrapped and converted to degrees, plus `m_angleOffset`. The IMU yaw is already counter-clockwise positive, so it is not negated as the old NavX reading was. `setHeading` and `resetOdometry` reset the gyro and store the offset.
  - **Teleop driving.** `drive()` does REV-style polar slew-rate limiting (using `SwerveUtils`) and applies an optional gyro-drift bias (`setGyroBias`). `getDefaultDriveController()` binds Xbox throttle buttons and installs `DriveCmd` as the default command. The effective throttle is the minimum of the driver throttle and the engineer throttle.
  - **Autonomous with Choreo.** `AutoFactory` is built with alliance flipping enabled. A TODO in the constructor explains how to fall back if red-side autos misbehave. `buildTrajectory(name, headingController[, resetPose])` returns a trajectory command. `followTrajectory()` adds feedforward from the sample plus x/y/heading PID in field frame, converts to robot-relative speeds, and logs the result to AdvantageKit `Logger` under `Choreo/`, `Drive/`, and `PID/`.
- **`Vision`** (`SubsystemBase`): a PhotonVision camera wrapper. It estimates pose with coprocessor multi-tag first, falls back to lowest ambiguity, and produces dynamic standard deviations (single-tag and multi-tag settable). `DriveTrain.periodic()` consumes it and also tracks the nearest AprilTag (`getNearestTargetPose()` and `getNearestTargetPoseStage()`, the latter offset by bumper distance).
- **`SwerveUtils`**: pure static angle math (step toward, wrap, angle difference). It is the only unit-tested code.

Units: the robot project passes inputs to `drive()` normalized to [-1, 1], and they are scaled by `maxSpeedMPS` and `maxAngularSpeed`. Odometry is in meters and radians. Telemetry X/Y readouts are in inches.
